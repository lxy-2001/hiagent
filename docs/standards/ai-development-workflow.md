# AI 协作开发与项目实现规范

## 1. 文档目的

本文规定如何在当前 AgentFlow-Java 项目基础上，借助 AI 持续设计和实现一个规范、完整、可维护的项目。

本文只定义开发流程、质量门禁和各 Skill 的职责，不包含具体功能方案，也不代表已经启动某个功能的设计或开发。

## 2. 推荐工具组合

推荐采用以下三层协作方式：

> Understand Anything 负责理解现状，Spec Kit 负责规格与设计，Superpowers 负责实现质量。

| 层次 | 工具或 Skill | 主要职责 |
|------|---------------|----------|
| 项目理解 | `understand-chat`、`understand-explain` | 基于知识图谱分析现有能力、依赖关系、影响范围和技术债 |
| 规格设计 | Spec Kit | 把想法转化为约束、需求、技术方案和可执行任务 |
| 质量保障 | Superpowers | 约束编码、调试、评审和完成前验证 |

三者不是互相替代的关系：

- **Spec Kit 是主流程和项目设计的“总导演”**，负责回答“做什么、为什么做、怎样拆分”。
- **Understand Anything 是现状分析工具**，负责回答“项目现在是什么样、修改会影响哪里”。
- **Superpowers 是实现阶段的质量护栏**，负责回答“怎样可靠地编码、调试和验收”。

不建议同时引入多套功能重叠的大型规划体系。规划结果应以 Spec Kit 产物为唯一依据，避免出现多份互相冲突的计划。

## 3. 总体流程

```text
理解现状
  ↓
确定项目目标和边界
  ↓
建立 Constitution（整个项目通常只做一次）
  ↓
拆分项目里程碑
  ↓
每个里程碑：
Specify → Clarify → Plan → Checklist → Tasks → Analyze
  ↓
人工批准
  ↓
TDD Implement → Debug → Code Review → Verification → Converge
  ↓
更新知识图谱和项目文档
  ↓
形成可演示、可测试、可说明的阶段成果
```

## 4. 阶段一：理解当前项目

在设计新能力前，先检查本地是否存在 `.ua/knowledge-graph.json`。已有且源码未变化时可直接复用，不需要每次重新扫描。新克隆仓库或图谱缺失时，先运行：

```text
$understand-anything:understand <仓库路径> --language zh
```

推荐问题：

```text
$understand-anything:understand-chat 当前项目已经具备哪些完整能力，哪些只是占位实现？

$understand-anything:understand-chat 当前项目的模块依赖方向和主要架构问题是什么？

$understand-anything:understand-chat 如果改造 Agent Runtime，会影响哪些文件和模块？

$understand-anything:understand-explain agent-web/src/main/java/com/agentflow/web/DefaultAgentRuntime.java
```

本阶段至少需要得到：

- 已实现能力和未完成能力清单；
- 核心调用链和模块依赖关系；
- 架构约束、明显技术债和高风险区域；
- 后续改造的影响范围；
- 可以保留、替换和新增的部分。

不要只根据 README 规划功能。README 可能落后于代码，重要结论应以代码、配置、测试和知识图谱互相印证。

## 5. 阶段二：建立项目级原则

使用：

```text
$speckit-constitution
```

Constitution 用来记录长期稳定的项目原则，例如：

- 模块职责和依赖方向；
- 高内聚、低耦合以及接口隔离要求；
- Java 编码约定和异常处理规范；
- 测试策略与最低质量要求；
- 安全、隐私和密钥管理要求；
- 可观测性要求；
- 文档同步要求；
- 禁止无依据增加抽象或依赖；
- 完成定义（Definition of Done）。

对应产物：

```text
.specify/memory/constitution.md
```

Constitution 是项目级规范，通常建立一次并持续维护，不应为每个小功能重新创建。

## 6. 阶段三：制定项目路线图

不要把整个项目写成一个巨大 Spec。应先将目标拆成多个能够独立演示、测试和验收的里程碑。

一个 Agent 项目可以按实际需要考虑以下方向，但最终选择必须以当前代码和项目定位为依据：

- Agent Runtime 与执行循环；
- 工具调用和 MCP 集成；
- 会话记忆与长期记忆；
- RAG 检索与知识管理；
- 任务规划、状态管理和恢复；
- 模型适配、路由与降级；
- 评测体系；
- 安全与权限；
- 可观测性与成本统计；
- API、控制台或演示体验；
- 部署、CI/CD 和项目文档。

每个里程碑都应形成一个独立的 Spec Kit 功能目录，而不是一次性规划所有实现细节。

## 7. 阶段四：逐个里程碑完成规格设计

### 7.1 Specify：定义需求

使用：

```text
$speckit-specify
基于当前项目实现【里程碑名称】。
目标：
用户价值：
范围：
非目标：
成功条件：
```

这一阶段只描述需求和验收结果，不急于指定类名、数据库表或具体框架。

典型产物：

```text
specs/XXX-feature/spec.md
```

### 7.2 Clarify：消除歧义

使用：

```text
$speckit-clarify
```

重点确认：

- 用户和使用场景；
- 范围与非目标；
- 异常和边界条件；
- 兼容性要求；
- 性能、安全和数据约束；
- 可量化的验收标准。

如果关键问题尚未明确，不进入技术方案阶段。

### 7.3 Plan：生成技术方案

使用：

```text
$speckit-plan
```

技术方案应结合现有代码，明确：

- 修改和新增哪些模块；
- 依赖方向是否符合 Constitution；
- 核心接口、数据模型和调用流程；
- 需要引入的外部依赖及理由；
- 错误处理、幂等性和并发策略；
- 安全、可观测性和性能设计；
- 测试方案、迁移方案和回滚方案；
- 文档更新范围。

典型产物：

```text
specs/XXX-feature/plan.md
```

### 7.4 Checklist：检查需求质量

使用：

```text
$speckit-checklist
```

Checklist 用来检查需求和方案是否完整，而不是代替代码测试。至少应覆盖：

- 功能和非功能需求；
- 边界条件与失败场景；
- 安全与隐私；
- 数据一致性；
- 可观测性；
- 测试与验收；
- 文档和演示。

### 7.5 Tasks：拆成可执行任务

使用：

```text
$speckit-tasks
```

任务应满足：

- 有明确顺序和依赖关系；
- 每个任务足够小，能独立验证；
- 明确涉及的文件或模块；
- 测试任务与实现任务配套；
- 优先形成最小可运行的纵向切片；
- 不把多个无关改动塞进同一任务。

典型产物：

```text
specs/XXX-feature/tasks.md
```

### 7.6 Analyze：实施前一致性检查

使用：

```text
$speckit-analyze
```

确认 `spec.md`、`plan.md`、`tasks.md` 与 Constitution 之间没有：

- 需求遗漏；
- 互相矛盾；
- 重复任务；
- 无法验证的成功条件；
- 违反架构原则的设计；
- 未进入任务列表的重要工作。

分析未通过时，先修改文档，不要急于编码。

## 8. 阶段五：人工批准门禁

AI 完成规格和计划后，开发者至少应确认：

- 这个里程碑是否真的值得做；
- 是否解决了明确问题；
- 范围是否过大；
- 技术方案是否符合项目定位；
- 是否引入不必要的框架、抽象或基础设施；
- 验收标准是否可以实际验证；
- 是否适合作为简历中的可说明成果。

未经批准，不进入批量实现阶段。AI 可以提出方案，但项目方向、范围和重要权衡应由开发者决定。

## 9. 阶段六：按任务实施

使用 `speckit-implement` 执行 `tasks.md`，同时用测试驱动开发约束每个任务：

```text
$speckit-implement
实施当前里程碑，但必须遵循 test-driven-development：
每次只处理一个任务；
先编写失败测试并确认正确失败；
再编写最小实现；
测试通过后才允许重构；
不得提前实现后续任务。
```

### 9.1 测试驱动开发

对每项功能或缺陷修复使用：

```text
$test-driven-development
```

基本循环：

```text
编写失败测试 → 确认测试按预期失败 → 最小实现
→ 确认测试通过 → 重构 → 再次验证
```

测试应优先验证外部行为和模块契约，避免只验证实现细节。

### 9.2 系统化调试

遇到测试失败、运行异常或行为与预期不符时使用：

```text
$systematic-debugging
```

先复现和定位根因，再修复。不要在缺少证据时连续试错式修改代码。

### 9.3 代码评审

任务或里程碑完成后使用：

```text
$requesting-code-review
```

收到评审意见后使用：

```text
$receiving-code-review
```

评审重点包括：

- 需求是否完整实现；
- 模块边界和依赖方向是否正确；
- 是否存在不必要耦合或过度抽象；
- 异常、安全、并发和数据一致性是否妥善处理；
- 测试是否覆盖主要路径和失败路径；
- 命名、注释和文档是否准确。

评审意见必须经过技术验证，不应机械接受或忽略。

### 9.4 完成前验证

宣布完成、提交合并或发布前使用：

```text
$verification-before-completion
```

必须运行与改动风险相匹配的最新验证命令，并检查真实输出。不能用“应该通过”“之前通过”代替当前证据。

## 10. 阶段七：检查实现是否收敛

使用：

```text
$speckit-converge
```

它用于将当前代码与 Spec、Plan 和 Tasks 对照，找出仍未实现的工作并补充到任务列表。

如果新增了任务，应继续：

```text
Implement → Review → Verification → Converge
```

直到没有必要的未完成项。Converge 不是无限增加功能，非目标和下一里程碑内容不应被偷偷加入当前范围。

## 11. 阶段八：更新知识与展示材料

每个重要里程碑完成后：

- 对改动范围进行增量知识图谱更新；
- 更新 README、架构、API、配置和部署文档；
- 保存测试、评测和性能结果；
- 准备可重复运行的演示；
- 记录关键设计决策和取舍；
- 必要时创建 Release 或里程碑标签。

这些产物能证明项目不仅“有代码”，而且具备工程完整性、可验证性和可说明性。

## 12. 质量门禁

一个里程碑只有同时满足以下条件才算完成：

- [ ] `spec.md` 的需求和成功条件清晰、可验证；
- [ ] `plan.md` 符合 Constitution 和现有架构；
- [ ] `tasks.md` 中的当前范围任务均已处理；
- [ ] 功能测试遵循先失败、再实现、再重构的过程；
- [ ] 主要成功路径、失败路径和边界条件有测试；
- [ ] 代码评审发现的问题已处理或有明确说明；
- [ ] 完成前验证使用的是最新代码和最新命令输出；
- [ ] Converge 未发现当前范围内的必要缺口；
- [ ] 相关文档、配置示例和演示已经同步；
- [ ] 没有提交密钥、个人数据或无关生成文件。

## 13. 核心执行原则

1. **先理解，再设计。** 任何重要设计都必须以当前代码事实为基础。
2. **一个里程碑一个 Spec。** 保持范围清晰，避免一次规划整个项目的全部细节。
3. **规划只有一个事实来源。** Spec Kit 产物是需求、计划和任务的正式依据。
4. **先完成纵向切片。** 优先打通一个可运行、可测试、可演示的完整流程。
5. **测试先于实现。** 对新增功能和缺陷修复使用测试驱动开发。
6. **保持高内聚、低耦合。** 把变化限制在清晰边界内，通过稳定接口协作。
7. **避免面向潮流堆技术。** 新技术只有在解决明确问题且收益可验证时才引入。
8. **不要过早追求复杂的多 Agent、A2A 或分布式架构。** 先保证单 Agent 核心闭环可靠，再按实际需求扩展。
9. **AI 不能替代关键决策。** 需求边界、重大依赖和架构取舍需要人工批准。
10. **没有验证证据就不宣布完成。** 测试、构建、评审和文档都属于交付的一部分。

## 14. 推荐的单里程碑命令顺序

```text
# 了解影响范围
$understand-anything:understand-chat ...
$understand-anything:understand-explain ...

# 规格与方案
$speckit-specify
$speckit-clarify
$speckit-plan
$speckit-checklist
$speckit-tasks
$speckit-analyze

# 人工审阅并批准

# 实现与质量
$speckit-implement
$test-driven-development
$systematic-debugging          # 仅在出现异常时
$requesting-code-review
$receiving-code-review         # 收到评审意见时
$verification-before-completion
$speckit-converge
```

不应为了“走流程”机械调用全部 Skill。每个 Skill 应在其对应阶段使用，其中 Constitution 通常按项目维护，Systematic Debugging 仅在遇到问题时使用。
