# Feature Specification: 工程基线与 Starter 边界

**Feature Branch**: `feature/001-engineering-baseline-starter`（当前实施分支）

**Created**: 2026-08-31

**Status**: VERIFIED

**Roadmap Feature**: Feature 001 — 构建、测试和装配边界可信

**Input**: User description: "为 HiAgent 建立可复现的工程基线，验证当前 Demo 和跨模块自动配置，
明确 Runtime、适配器、自动配置、Starter 与 Demo 的边界，并禁止生产路径用 Noop、Fake
或无凭据兜底结果伪装成功；本 Feature 不实现新的 Agent 能力。"

## Feature Outcome *(mandatory)*

**Unique Result**: 开发者可以从干净仓库使用一个受支持的统一命令验证全部模块，并确认
Demo 通过显式、可覆盖的模块装配加载当前 Web 入口和 Runtime；缺少真实能力时系统给出
明确失败或禁用结果，而不是伪造成功。

**Why Now**: 后续 Runtime、Run、记忆、RAG、MCP 和评测 Feature 都依赖可信的构建与装配
基线。如果当前模块只能依靠偶然扫描、手工导入或静默占位实现工作，后续测试无法区分
真实能力与错误装配。

## Clarifications

### Session 2026-09-01

- Q: Feature 001 应如何处理当前 HTTP 接口？ → A: 仅验证现有接口能够注册和基本调用，全部
  视为临时 Demo 接口；稳定 Run/SSE API 留到 Feature 003。
- Q: 当前稳定框架版本是否只记录、不迁移？ → A: 迁移到 Java 17 可运行的当前稳定
  Spring Boot 4.1.1，并把主版本迁移放在独立 Phase；先验证最新 3.5.x 过渡基线，迁移失败
  不得通过弱化测试或混入功能修改来绕过。
- Q: 删除 Noop RAG 后，当前 Runtime 如何处理缺失的 `RagRetriever`？ → A: 当前 Runtime
  构造函数仍把它视为必需端口；Demo 提供真实实现，其他消费应用未提供时必须在装配阶段
  明确失败。RAG 是否成为可选能力及其运行语义由 Feature 005 重新设计。
- Q: Feature 001 是否拆分 `agent-web` 当前聚合的所有可选技术依赖？ → A: 不拆分；本 Feature
  只验证精确自动配置、覆盖退让和真实失败。最终按需适配器与 Starter 依赖拆分由
  Feature 008 负责，当前聚合必须被明确记录为临时边界。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 使用统一命令验证仓库 (Priority: P1)

作为项目贡献者，我希望从干净检出的仓库使用仓库提供的统一命令完成全部模块的构建和
自动化验证，从而确认本地与持续集成环境执行的是同一套质量门禁。

**Why this priority**: 没有可复现的构建入口，任何后续 Feature 的测试结果都不可可靠复现。

**Independent Test**: 在仅具备受支持运行环境、不配置真实模型凭据且不连接不可控外部
服务的环境中执行文档指定的唯一验证命令，观察全部模块和测试是否成功结束。

**Acceptance Scenarios**:

1. **Given** 干净检出的仓库和受支持的运行环境，**When** 开发者执行统一验证命令，
   **Then** 所有模块完成编译和测试，并返回成功状态。
2. **Given** 未提供真实模型 API Key 且没有启动外部模型服务，**When** 执行默认验证，
   **Then** 验证仍可使用受控测试替身完成，不发生真实付费调用。
3. **Given** 本地与持续集成环境使用同一仓库版本，**When** 分别执行标准验证，
   **Then** 两处使用相同入口和相同必需质量门禁。
4. **Given** 当前 Spring Boot 3.5.x 工程基线，**When** 完成独立兼容性迁移 Phase，
   **Then** 项目在 Java 17 与 Spring Boot 4.1.1 上通过完整门禁，且迁移差异没有夹带新的
   Agent 产品行为。

---

### User Story 2 - 显式加载并覆盖可复用组件 (Priority: P2)

作为使用 HiAgent 模块的应用开发者，我希望应用只需引入公开模块并启动正常的应用上下文，
就能加载当前承诺的 Web 入口、Runtime 和必要适配器；当应用提供自定义实现时，默认实现
应主动退让。

**Why this priority**: 这证明模块可以作为轮子被消费，而不是依赖 Demo 根包扫描或手工导入
内部配置才能工作。

**Independent Test**: 使用最小应用上下文分别验证默认装配和应用自定义实现装配，检查公开
入口、关键组件及最终选中的实现。

**Acceptance Scenarios**:

1. **Given** Demo 只使用公开模块和标准自动配置发现机制，**When** 应用上下文启动，
   **Then** 当前承诺的 Web 入口、Runtime 和必要组件均可被发现。
2. **Given** 应用提供一个已声明替换点的自定义实现，**When** 应用上下文启动，
   **Then** 使用自定义实现且对应默认实现不再创建。
3. **Given** 应用缺少执行某项必需能力的真实实现，特别是当前 Runtime 必需的
   `RagRetriever`，**When** 装配 Runtime 或请求使用该能力，**Then** 系统明确报告未配置或
   不可用，不注册 Noop，也不返回伪造的成功内容。
4. **Given** 某项后续 Feature 能力尚未启用，**When** 应用启动，
   **Then** 该能力被明确标识为未启用，且不会产生看似成功的空结果或测试结果。

---

### User Story 3 - 保护模块边界和当前 Demo 入口 (Priority: P3)

作为项目维护者，我希望自动化检查保护纯核心模块、适配器、Web、Demo 和未来 Starter 的
职责边界，并验证当前临时 Demo HTTP 入口能够通过显式装配注册和基本调用，而不在本
Feature 中冻结最终公开 API。

**Why this priority**: 边界一旦在后续 Feature 中被破坏，Runtime 会重新与框架和基础设施
耦合，最终难以复用和讲解。

**Independent Test**: 执行架构和应用启动检查，确认核心模块没有框架或基础设施依赖；
检查当前 Demo 入口清单及其注册和基本调用验证，确认没有被误标为稳定公开契约。

**Acceptance Scenarios**:

1. **Given** 当前模块依赖图，**When** 执行架构边界检查，**Then** 纯核心模块不依赖
   Spring、数据库、缓存、向量库、HTTP 或模型厂商 SDK。
2. **Given** Demo 应用启动，**When** 检查跨模块组件来源，**Then** 可复用组件由显式模块
   装配提供，不依赖扩大 Demo 根包扫描。
3. **Given** 当前 HTTP 操作清单，**When** 审查接口状态和测试，**Then** 每个操作都被标记
   为临时 Demo 接口，当前承诺入口具有注册和基本调用验证，且不形成稳定公开契约承诺。
4. **Given** 当前框架和模型连接依赖，**When** 审查兼容性记录，**Then** 支持版本、验证
   依据、已知风险和后续升级条件均有明确结论。
5. **Given** 版本控制中的生产源码和配置，**When** 检查模型 Key、JWT Secret、数据库密码
   和初始化管理员凭据，**Then** 不存在可直接使用的真实值或通用默认密码，测试值只存在于
   测试配置。

### Edge Cases

- 仓库运行环境不满足支持版本时，统一命令应快速给出可理解的版本或环境错误。
- 模型凭据为空、无效或真实服务返回空响应时，不得转成确定性生产回答或向量后继续成功。
- 应用同时提供多个互斥实现时，应明确拒绝歧义或遵循已记录且可测试的选择规则。
- 最终 Starter 的可选适配器未引入时不得强迫应用加载其基础设施依赖；该依赖级拆分属于
  Feature 008。本 Feature 只保证当前已引入模块不会通过扫描或 Noop 偶然装配。
- 外部数据库、缓存、向量库或模型服务未启动时，默认测试不得因此失败或尝试联网。
- 当前 Demo 中已经存在的实现和测试必须通过证据确认，不能仅因文件存在就视为满足需求。
- 当前 Runtime 的算法或模块归属问题不得借工程基线之名被提前重写。
- Boot 4 迁移遇到不兼容时必须保留失败证据并修正迁移，不得删除、跳过或弱化测试。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仓库 MUST 提供一个受版本控制的统一验证入口，用于构建并测试所有模块。
- **FR-002**: 默认验证 MUST 在没有真实模型凭据、真实生产数据和不可控外部服务的条件下
  可重复执行。
- **FR-003**: 持续集成 MUST 使用与本地相同的统一验证入口和受支持运行环境。
- **FR-004**: Demo 的完整应用上下文 MUST 能通过显式模块装配加载当前承诺的 Web 入口、
  Runtime、持久化组件和必要适配器。
- **FR-005**: 跨模块组件 MUST NOT 依赖扩大应用根包扫描或应用手工导入模块内部配置而
  偶然加载。
- **FR-006**: 每个由本 Feature 承诺的应用覆盖点 MUST 具有自动化验证，证明应用自定义
  实现存在时默认实现会退让。
- **FR-007**: 缺少必需提供者、凭据或实现时，系统 MUST 在启动相关能力或请求使用该能力
  时返回明确的配置或不可用结果。
- **FR-008**: 生产路径 MUST NOT 把 Noop、Fake、确定性测试回答、确定性测试向量或空占位
  Tool 当作真实能力成功。
- **FR-009**: 尚未实现的可选能力 MUST 被明确视为未启用，不得伪装成成功执行。
- **FR-010**: 自动化架构检查 MUST 证明纯核心模块不依赖框架、传输、存储和厂商基础设施。
- **FR-011**: 当前 HTTP 操作 MUST 全部标记为临时 Demo 接口；本 Feature MUST 验证当前
  承诺入口能够注册和基本调用，但 MUST NOT 冻结最终公开 API，稳定 Run/SSE 契约由
  Feature 003 定义。
- **FR-012**: 本 Feature MUST 将工程迁移到 Java 17 可运行的 Spring Boot 4.1.1 当前稳定
  基线，并记录模型连接依赖的兼容性结论、验证依据、风险和升级条件；主版本迁移 MUST 位于
  独立 Phase，先验证最新 3.5.x 过渡基线，再通过完整门禁证明最终版本。
- **FR-013**: Demo 启动和组件装配验证 MUST 不要求真实模型付费调用。
- **FR-014**: 版本控制中的生产源码与配置 MUST NOT 包含模型 Key、JWT Secret、数据库
  密码或初始化管理员通用默认密码；本 Feature 只把这些值迁移到环境变量或测试配置，
  MUST NOT 借此重构身份和数据库业务。

## Scope Boundaries *(mandatory)*

### In Scope

- 统一的仓库构建与测试入口及其使用说明。
- 与统一入口一致的最小持续集成验证。
- 当前 Demo 完整应用启动、Web 入口注册和关键组件装配验证。
- 当前自动配置的发现、条件退让和缺失能力语义。
- 纯核心模块的依赖边界自动化保护。
- 当前临时 Demo HTTP 操作清单、入口注册和基本调用验证。
- Java 17 上的 Spring Boot 4.1.1 独立兼容性迁移，以及模型连接兼容性结论。
- 移除版本控制中生产配置的通用默认凭据，并提供非秘密环境变量示例和测试配置。

### Out of Scope

- 新增、迁移或重写 Agent 决策循环、预算、取消和终止算法；由 Feature 002 负责。
- 为解决当前 Runtime 所在模块而提前实施 Feature 002；本 Feature 只记录临时边界和退出点。
- 设计最终 Run/SSE API、事件重放和取消协议；由 Feature 003 负责。
- 实现新的记忆、RAG、MCP、审批或评测能力；由后续对应 Feature 负责。
- 正式创建和发布最终 HiAgent Starter；本 Feature 只定义并验证自动配置和未来 Starter
  必须遵循的边界，最终收口由 Feature 008 负责。
- 拆分 `agent-web` 当前聚合的 LLM、RAG、JPA、Redis、Security 依赖，或完成最终按需
  适配器组合；由 Feature 008 负责。
- 重构现有身份、数据库、缓存或 Demo 业务功能，除非它们直接阻止本 Feature 的启动与
  装配验收。
- 微服务、分布式执行、生产部署、Kubernetes、复杂权限和产品级前端。

### Dependencies

- 无前置 Feature。
- 依赖当前仓库中已有模块和 Demo 作为起始基线。
- 依赖一个受支持的本地运行环境；具体版本和兼容性选择在规划阶段形成决策记录。

## Portfolio Evidence *(mandatory)*

- **Code Path to Explain**: 从应用启动、自动配置发现、条件覆盖到 Runtime 被注入的完整
  装配路径，以及纯核心模块的依赖保护。
- **Runnable Scenario**: 从干净仓库执行一次统一验证，再运行默认装配与自定义覆盖两个
  最小应用场景。
- **Measurable Evidence**: 全仓验证结果、完整应用启动结果、临时 Demo 入口注册和基本调用
  检查、覆盖行为检查、架构依赖检查和持续集成结果。
- **Build-vs-Reuse Story**: 项目负责模块边界、替换语义和真实失败规则；复用构建工具、
  应用生命周期、测试框架和持续集成运行环境。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在干净仓库中，一个文档化命令能够执行 100% 模块的编译和自动化测试并以
  成功状态结束。
- **SC-002**: 默认验证场景产生 0 次真实付费模型调用，且不要求启动数据库、缓存、向量库
  或其他不可控外部服务。
- **SC-003**: 本地和持续集成均使用同一个仓库验证入口，并对同一提交给出一致的通过或失败
  结论。
- **SC-004**: 完整应用启动验证能够发现 100% 已记录的必需组件和当前承诺入口。
- **SC-005**: 100% 已记录的默认替换点至少具有一个应用自定义实现覆盖测试。
- **SC-006**: 缺少模型凭据、必需实现或有效响应的验收场景中，0 个场景返回伪造成功。
- **SC-007**: 架构检查发现纯核心模块中的框架或基础设施依赖数量为 0。
- **SC-008**: 当前 HTTP 操作清单覆盖率为 100%，全部标记为临时 Demo 接口，当前承诺入口
  的注册和基本调用检查全部通过。
- **SC-009**: 新开发者按照快速验证说明，在依赖已缓存、未启动外部运行服务的正常开发环境中，
  从执行统一验证命令到进程结束的墙钟时间必须不超过 600 秒；在该时限内获得完整成功或
  具有明确原因的失败结果才算通过，超过 600 秒必须记录为未通过并说明原因。这里的“通过”
  仅表示耗时门禁通过；命令是否满足功能要求仍由 SC-001 等其他标准单独判定。
- **SC-010**: Java 17 与 Spring Boot 4.1.1 的最终组合通过 100% 全仓门禁；Spring AI 在
  未被实际适配和测试前不被声明为受支持或已验证兼容。
- **SC-011**: 版本控制中的生产源码和配置发现模型 Key、JWT Secret、数据库密码或初始化
  管理员通用默认密码的数量为 0。

## Assumptions

- V1 仍按单进程模块化应用开发，本 Feature 不引入分布式执行。
- 默认测试通过确定性测试替身隔离外部服务，但测试替身不会进入生产装配。
- 缺少真实模型凭据时允许应用基础上下文启动；首次请求真实模型能力时必须明确失败。
- 当前 Runtime 仍要求真实 `RagRetriever`；Demo 提供现有真实实现，其他消费应用未提供时
  允许在 Runtime 装配阶段明确失败，而不是注册 Noop。
- 当前 Demo 中的身份、数据库和缓存代码属于历史基线，不因本 Feature 自动升级为 V1
  必需能力。
- 当前 Runtime 的实现位置作为经 Feature 计划批准的临时架构例外记录；本例外在 Feature
  002 完成时到期，由 Feature 002 迁入 `agent-core`，Feature 001 不改变其算法。
