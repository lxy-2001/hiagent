# Feature Specification: 010 / H01 上下文与会话历史升级

**Feature Branch**: codex/010-context-history-compaction（计划实施分支，尚未创建）；本轮仅完成SDD文档，不切换当前代码分支。

**Created**: 2026-10-06

**Status**: Planned — 行为澄清完成，plan、tasks及配套契约已生成；59项任务待实施，Feature仍为ACTIVE。

**Roadmap Feature**: 010（第二阶段 H01）/ 可恢复、有容量边界的连续会话上下文。

**Input**: 用户要求基于 HiAgent 复用现有 Runtime；先固定并澄清H01规格，现已明确要求按Spec Kit生成具体plan、tasks等SDD文件。

## Feature Outcome *(mandatory)*

**Unique Result**: 一个会话能够跨 Run 保留用户、模型与工具的实际交互；运行时持续追加有效上下文，在接近容量上限时压缩旧前缀并保存检查点；大内容作为本地工具输出附件保存和按需读取，空间充足时长期保留，空间不足时按会话与全局限额淘汰最久未使用的附件。重新打开会话后，可以恢复已确认的上下文，而不自动重放操作。

**Why Now**: 现有上下文偏向单 Run 的工具交互和跨 Run 的成功问答，无法充分承载后续 Harness 长任务。H01 先形成历史、容量、压缩、附件和模型适配的完整基础，H02–H04 再接入任务进度、文件及终端能力。

**本轮交付边界**: 本文件固定行为要求、默认参数和验收方向；Q1–Q3均已关闭。实现设计见[plan.md](plan.md)，任务见[tasks.md](tasks.md)，验证流程见[quickstart.md](quickstart.md)。本轮完成技术设计、数据模型、契约和任务拆分；产品代码、数据迁移/清理、提交与推送均未开始。

**已有决定来源**: [第二阶段约定](../stage-02-harness/planning/implementation-spec.md)、[讨论记录](../stage-02-harness/discussion.md)。被本规格明确吸收的 H01 要求进入正式范围；其他 Feature 的内容不因此成为 010 验收条件。

## Clarifications

### Session 2026-10-06

- Q: 历史保存失败时怎样继续？ → A: 用户确认有限重试；耗尽后停止本次 Run 的后续新动作，只补写原记录，绝不自动重做已经执行的工具。状态必须区分已执行、已保存和未确认。
- Q: 重试次数与等待多久？ → A: 用户授权选择合理默认值；本规格采用首次尝试加最多 3 次重试，间隔 200/500/1,000 毫秒，重试窗口 10 秒，可配置并受取消和 Run 剩余预算约束。
- Q: 附件保存多久、容量怎样设置？ → A: 不按天数过期，空间充足时长期保留；删除会话后自动清理关联附件。用户随后确认会话级限额与全局按最近使用时间淘汰，替代“只要会话还在就绝不删除附件”的解释；具体规则见下一项。
- Q: 容量是否按线程限制、全局满了按什么顺序清理？ → A: 用户确认按会话（thread/session，非 Java 工作线程）分别限制附件容量，并在全局空间不足时优先清理上次使用时间最早的闲置会话附件。默认每会话 512 MiB、清理目标 384 MiB；全局 5 GiB、目标 4 GiB；单件仍为 64 MiB，均可配置。保留会话、消息和执行事实，只回收符合条件的附件正文并标记已清理；活动 Run 和读写中的内容受保护。
- Q: 旧 MySQL 历史需要迁移或兼容读取吗？ → A: 不需要。用户确认现有历史均无保留需求，H01 按全新本地数据落地；不做迁移、双读或旧历史归档。旧项目库后续可在准确识别后处理，本轮不执行删库。
- Q: 压缩程度与相关参数怎样确定？ → A: 用户希望至少约 5 倍压缩并允许调整；按 Token 设置目标，压缩后摘要加保留尾部不超过压缩前可压缩历史的 20%，有效规则和工具定义不纳入该比例。默认参数由代理按授权选定，见下表；不得为满足比例破坏工具配对或伪造摘要成功。

### 本次测试范围约定（2026-10-06）

用户明确要求按个人简历项目规模设计测试。关键行为保留TDD、目标失败证据及必要的正常/失败/边界场景；同一行为只设一个主要验证位置，跨层仅补接入检查，优先复用现有回归。保留一条完整端到端主线，不要求每个record、字段或存储表单独建测试，也不建设压力/浸泡、真实磁盘写满、硬件断电或穷举故障矩阵。每阶段运行受影响模块，最终运行一次全仓验证；同一代码状态的有效证据可复用，已有测试不得删除、跳过或弱化。功能要求和成功标准保持不变。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 恢复会话时知道之前实际做过什么 (Priority: P1)

用户关闭并重新打开会话，仍能查看已保存的交互。下一次 Run 获得适用的旧上下文，知道之前读过什么、调用过什么、哪里失败过，不只看到成功问答。

**Why this priority**: 后续连续任务和上下文压缩都依赖有序、可恢复的历史。

**Independent Test**: 使用确定性模型和工具产生两次 Run，包含成功结果和失败结果；关闭并重建会话工作状态，核对存储记录与实际送模序列。

**Acceptance Scenarios**:

1. **Given** 同一会话有用户消息、模型文本、工具调用和结果，**When** 下一次 Run 恢复上下文，**Then** 适用消息保持顺序和调用关联；同次响应内的模型文本与工具调用均不会丢失。
2. **Given** 一次 Run 失败或取消，**When** 恢复会话，**Then** 已确认的失败或取消事实仍可查，缺失结果明确标为未知；不补造成功、不重新执行旧工具。
3. **Given** 已有摘要覆盖一段旧历史，**When** 重开会话，**Then** 用已提交摘要和未覆盖消息恢复，不把已覆盖原文再次全量加载进模型窗口。
4. **Given** 会话工作状态仍在内存，**When** 正常进入下一轮，**Then** 只维护新增内容；查询历史记录可独立分页，不要求所有会话常驻内存。

### User Story 2 - 长会话在容量边界内继续 (Priority: P1)

用户执行较长任务时，模型在容量充足时尽量看到连续历史；接近上限时，较早内容被整理为可接续工作的摘要，最近交互仍保留。

**Why this priority**: 仅提高配置窗口而保留旧消息限制，不能解决长任务上下文问题。

**Independent Test**: 使用可预测 Token 计数和摘要响应，覆盖未触发、触发、加入大消息、连续两次压缩及重启恢复的情况。

**Acceptance Scenarios**:

1. **Given** 请求未到压缩阈值且能够容纳，**When** 追加新交互，**Then** 不调用摘要模型，不重扫全部历史；连续顺序保持稳定。
2. **Given** 请求达到配置的压缩阈值，或新消息使请求预计放不下，**When** 准备下一次模型调用，**Then** 先在合法工具消息边界处理旧前缀，保留最近连续交互；按配置将摘要与保留尾部的合计 Token 目标控制到原历史的 20% 以内，检查点保存成功后才启用。
3. **Given** 会话已有摘要，**When** 再次需要压缩，**Then** 合并旧摘要与新变旧的前缀，不反复全量读取被覆盖原文，也不重复拼接保留尾部。
4. **Given** 摘要失败、不完整、超限或保存失败，**When** 决定是否继续，**Then** 不启用半成品；模型摘要失败且旧窗口能容纳时可沿用，否则报告明确容量/压缩问题。持久化故障先按 FR-029 补写，重试耗尽后即使旧窗口能容纳也停止新动作；不无限重试。

### User Story 3 - 大日志按需查看，附件有明确保留与容量边界 (Priority: P1)

用户运行工具后，模型获得真实执行状态、有限内容预览和附件引用；需要细节时能够按范围读取。附件在空间充足时长期保留，删除会话后自动清理；会话或全局额度不足时按最近使用时间淘汰旧附件，保留消息、执行事实和不可用标记，不能把已清理或未保存内容报告为可完整读取。

**Why this priority**: 单次大输出就可能占满窗口，不能只依赖多轮历史压缩。

**Independent Test**: 确定性工具生成超预览但未超单件配额的内容；核对全文、预览及分段读取。用多个会话和可控使用时间，分别验证单会话限额、全局淘汰顺序、最近使用刷新、活动保护、会话删除清理及无法释放空间时的错误反馈。

**Acceptance Scenarios**:

1. **Given** 工具输出过大，**When** 执行层处理结果，**Then** 内容保存为可定位的本地附件；模型得到真实状态、有限预览和引用，不必额外要求模型调用保存工具。
2. **Given** 附件可用且当前调用者有权访问，**When** 使用 read-artifact 请求合法范围，**Then** 返回对应内容，返回大小仍受限；恢复历史不会自动展开所有附件。
3. **Given** 附件所属会话仍存在且空间足够，**When** 时间流逝，**Then** 不因附件变老自动删除；用户删除会话后，在活动使用结束时自动清理关联附件，工程源文件不受影响。
4. **Given** 单会话附件将超 512 MiB，**When** 执行容量处理，**Then** 只从该会话内按附件最后访问时间由旧到新清理未受保护的附件，目标降至 384 MiB；不得用其他会话的空余配额绕过本会话限制。
5. **Given** 全局附件将超 5 GiB，**When** 清理已删除会话附件和可删临时文件仍不足，**Then** 跳过有未结束 Run 的会话，按其余会话最后使用时间由旧到新选择，再按会话内附件最后访问时间清理，目标降至 4 GiB。最近重新使用的会话排序后移，后台轮询不刷新排序；不删除会话本身或改写执行事实。
6. **Given** 清理尚未达到目标，**When** 判断本次内容是否能保存，**Then** 会话和全局两级限额及磁盘空间均满足时可继续；只剩受保护内容、无可删对象或删除重试耗尽且仍无法保存时，明确报错，不无限清理或扩大到工程文件。
7. **Given** 附件未保存、已清理、被截断或无权访问，**When** 请求读取，**Then** 得到明确且不泄漏其他会话内容的结果，不返回虚构原文，不自动重跑原工具来冒充历史结果。

### User Story 4 - 用配置选择模型并理解实际容量和用量 (Priority: P2)

使用者通过配置选择默认模型，理解本次实际使用的窗口、压缩与用量；不需要先建设模型管理界面或计费平台。

**Why this priority**: H01 的容量边界必须与真实模型协议一致，缓存统计不能代替真实上下文管理。

**Independent Test**: 使用 Responses 协议样例验证文本、工具调用/结果、用量和错误映射；更换模型配置并重建下一次 Run，核对容量检查及缓存缺失字段。

**Acceptance Scenarios**:

1. **Given** 默认配置，**When** 创建模型请求，**Then** 使用 OpenAI Responses API 和 gpt-6.1-sol；工作窗口默认 272K，可从配置修改模型及适用容量，不要求前端模型目录。
2. **Given** 模型或容量配置变更，**When** 开始下一次 Run，**Then** 重新检查有效上下文和协议能力；不继续沿用不适用的旧窗口，也不因远端历史引用把已压缩原文又带回来。
3. **Given** 供应商报告缓存用量或未报告该值，**When** 展示运行记录，**Then** 有值则按实际记录，缺失为不可用；不伪造命中、不把缓存子项重复加到输入总量。

### User Story 5 - 存储或进程异常后仍诚实说明状态 (Priority: P1)

会话恢复和持久化出错时，用户能区分已保存、未确认和已实际执行的操作，避免因恢复再次修改文件或重复执行命令。

**Why this priority**: 展示事件丢失与恢复所需历史丢失影响不同，不能用相同的“忽略失败”承诺掩盖差异。

**Independent Test**: 注入可恢复及持续的消息写入、附件保存、摘要提交故障与进程中断，核对重试次数、动作是否继续、恢复记录和真实工具执行次数；副作用执行次数不随持久化重试增加。

**Acceptance Scenarios**:

1. **Given** 工具已经执行但持久化确认丢失，**When** 恢复会话，**Then** 不声称该操作从未发生或已经成功落盘，不自动重放副作用。
2. **Given** 消息或所需附件发生可重试的保存故障，**When** 尚有重试次数与时间预算，**Then** 暂停后续新动作，只重试同一逻辑写入；成功确认后可以继续，不能因为补写重复调用模型或工具。
3. **Given** 重试耗尽、取消或确认不可重试，**When** 该保存问题仍未解决，**Then** 停止后续新模型请求和工具动作；仍可报告错误、处理终态和释放资源。已经执行的工具不能自动重跑；终态本身无法持久化时，不显示为已持久确认成功。
4. **Given** 正常关闭后重新启动 Windows 本地应用，**When** 打开已有会话，**Then** 不依赖外部数据库服务即可恢复已提交记录；模型联网调用仍按其配置执行。

### Edge Cases

- 新消息、长工具参数或单个工具结果使容量突增；不能在执行前截断实际参数，或只限制 Tool Result 而忽略 Tool Call。
- 恢复时模型窗口变小、未覆盖尾部很大或多个会话并存；不得先把全库大内容加载到内存再检查。
- 工具调用缺少对应结果、重复交付同一记录或检查点边界切进配对中间；不能制造重复动作或伪造配对。
- 模型返回同次文本与工具调用、非正常结束的摘要或容量错误；不可丢掉可见文本，也不能启用不完整摘要。
- 摘要提交时取消、进程退出或写入结果不确定；恢复只能采用确认有效的检查点。同一逻辑写入重复提交须可识别，不产生重复消息；补写不能重调工具。
- 压缩后无法同时满足 20% 目标、必要信息和工具配对时，不启用不合规摘要；只在旧窗口仍可安全容纳时继续，否则明确报告问题。
- 附件清理与读取/写入并发、磁盘满、文件缺失或越界路径；需保护正在使用的内容，拒绝越权访问并说明不可用状态。
- 文件或工具输出包含要求改变规则的文字；摘要和上下文不得将其提升为系统指令或操作授权。
- 供应商不支持某缓存字段、未命中或用量不可得；普通请求仍按已支持能力工作，记录真实限制。

## Requirements *(mandatory)*

### Functional Requirements

**历史与工作上下文（US1、US5）**

- **FR-001**: 系统 MUST 按会话顺序记录用户消息、模型可见文本、工具调用、成功/失败结果以及已知取消事实；同次响应的文本与工具调用不得互相覆盖。记录工作消息不等于提前实现 H02 的阶段决策策略。
- **FR-002**: 记录 MUST 保留会话/Run 归属、稳定序号、发生时间和调用关联；恢复保持角色、顺序及合法工具配对，不要求把所有存储元信息写进 Prompt 正文。
- **FR-003**: 系统 MUST 以消息及其内容引用作为恢复依据；Step/Event 的展示摘要不得反向冒充完整会话历史，失败 Run 不得因未成功而丢弃其已确认交互。
- **FR-004**: 系统 MUST 在 Run 之间接收新用户消息；H01 不接入运行中用户追加或修改要求，不改变现有取消和审批入口。
- **FR-005**: 会话恢复 MUST 使用最近有效检查点和未覆盖记录，或在没有检查点时按容量读取历史；不得因恢复而全量展开旧附件或自动执行历史工具。
- **FR-006**: 工作上下文 MUST 支持持续追加；普通循环不得重扫全库或重新生成摘要。构造/发送完整模型请求与重建历史状态是不同操作。
- **FR-007**: 历史查看与恢复 MUST 有分页/分批和容量边界；闲置工作上下文允许释放，不要求所有会话常驻内存。完整保存历史不等于全量装入内存。

**容量与压缩（US2、US4）**

- **FR-008**: 默认工作窗口 MUST 为 272K；本文按 272,000 Token 表达该应用配置，模型能力与工作上限分别管理。窗口可配置，不得只修改显示数字而继续受不适用的旧固定窗口限制。
- **FR-009**: 每次请求前 MUST 估算规则、工具定义、已加载上下文材料、消息及长调用参数的完整输入，并预留输出和估算余量；默认单次模型输出上限 32,768 Token、安全余量 8,192 Token，均可配置。单次窗口、单次输出与整个 Run 的累计预算分别管理。
- **FR-010**: 系统 MUST 在预计完整输入达到工作窗口的 80%（默认 217,600 Token），或无法满足输入加输出预留及安全余量的边界时触发容量处理；实际阈值取两者较小值。软阈值可在已确认的 80%～85% 区间配置；新消息加入后、送模前必须复查。
- **FR-011**: 压缩 MUST 处理较早连续前缀，按容量保留最近连续交互，并避免拆开工具调用/结果或覆盖未决调用。默认目标为“新摘要 + 保留尾部”的 Token 合计不超过压缩前可压缩历史的 20%，比例可配置；系统规则、工具定义及其他单独受保护内容不计入压缩比例，但仍计入总窗口。原始记录不因上下文压缩被删除。
- **FR-012**: 摘要及覆盖范围 MUST 成功保存后才切换有效上下文；覆盖范围由程序依据记录确定，不能由摘要模型猜测。一次切换后不得重复拼接尾部或再次送入被覆盖原文。
- **FR-013**: 下一次压缩 MUST 可以基于旧摘要和新变旧的前缀继续；当前有效规则和目标来自权威来源，不仅依赖有损摘要。H02 的结构化计划在其实现后再接入。
- **FR-014**: 系统 MUST 为摘要设置独立、可审查的提示词和有界请求，要求保留目标、约束、修订、关键决定、事实与判断的区别、阻碍、未确认操作及必要文件/附件引用；不回答旧问题、不调用工具、不将外部内容升级为授权。
- **FR-015**: 摘要调用 MUST 受用量、时间和取消边界控制；失败、不完整、超限或无法在保留必要信息与合法配对的同时达到压缩目标时，不能启用半成品。摘要模型失败且旧上下文能容纳时可沿用，否则明确报告问题；检查点等持久化失败则按 FR-029 有限补写，耗尽后停止新动作。不得无限压缩重试或重放副作用。
- **FR-016**: 系统 MUST 记录压缩前后大小、覆盖范围及失败原因；实际模型仍报告容量问题时必须真实处理。估算不是厂商精确计费或模型永不超限的保证。

**工具输出附件（US3、US5）**

- **FR-017**: 单次大输出 MUST 能由执行层保存为本地 Artifact（工具输出附件），模型消息只携带真实状态、受限预览和内容引用；默认预览不超过 4,096 Token，普通小结果可直接保留。无需额外要求模型执行保存动作；保存限额与模型预览限额分开。
- **FR-018**: 附件 MUST 有可定位标识、归属、大小、时间及可用性信息；已保存范围内的内容可再次读取。默认单件内容上限 64 MiB，超过上限只保存受限内容并明确标记截断及已保存范围；不能通过自动拆分规避总配额。存储失败、截断和已清理均可辨别，不能声称不可用原文已完整保存。
- **FR-019**: 系统 MUST 提供按 ID 和范围读取附件的能力，校验归属/权限并限制返回大小；默认单次读取不超过 8,192 Token，仍受当前请求容量约束。拒绝越权和托管目录外访问，未知或已清理引用返回明确结果。
- **FR-020**: 系统 MUST 保留当时提供给模型的预览及引用关联；恢复时不能自动展开完整日志。源文件不必每次读取都复制，文件创建/修改后也不自动再塞入一份全文。
- **FR-021**: 长工具参数与结果 MUST 都计入容量处理；执行参数不得为适配窗口而提前截断，历史摘要或外置表示不得伪造真实操作。各工具具体内容策略在后续契约细化。
- **FR-022**: Harness MUST 同时按会话和全局管理托管附件容量。默认单会话高水位 512 MiB、清理目标 384 MiB；全局高水位 5 GiB、目标 4 GiB，均可配置，规则见下文。空间充足时不按天数过期；删除会话后清理关联附件。容量不足时无需逐次确认即可按最近使用时间清理未删除会话的旧附件；保护活动 Run 依赖与正在读写的内容，保留会话、历史消息、执行事实和已清理标记，不删除用户工程文件。清理后仍无法保存时按 FR-029 有限处理并停止新动作，不无限清理或伪报全文可读。

**本地存储、模型与真实用量（US1、US4、US5）**

- **FR-023**: H01 MUST 按 Windows 桌面方向落实本地持久化，使该能力正常运行无需外部数据库服务；结构化记录和大内容分别管理，默认应用数据目录为 %LOCALAPPDATA%\HiAgent，可配置到其他磁盘。数据库引擎在 plan 中核验已有迁移、事务及锁语义后选择；不要求本 Feature 完成桌面安装包。
- **FR-024**: 首批模型接口 MUST 使用 OpenAI Responses API，默认模型为 gpt-6.1-sol，允许配置替换；实际协议映射须保留文本与工具关联，具体提供方类型不得进入纯 Java Core。
- **FR-025**: 模型/窗口配置变更 MUST 在后续 Run 使用前校验；本地摘要切换后，不得借旧远端状态引用把已覆盖历史意外重新纳入请求。运行中不引入交互式模型切换。
- **FR-026**: 模型请求 SHOULD 保持有效规则前缀和工具顺序稳定，动态交互持续追加；真实规则变化、用户要求和必要压缩优先，不能为缓存保留过期信息。
- **FR-027**: 系统 MUST 记录供应商实际返回的总用量及可用缓存子项；缺失不编造，已报告零与不可用须区分。缓存子项不得重复累加，缓存折扣不减少逻辑上下文占用。
- **FR-028**: 会话、模型请求、检查点和附件 MUST 可关联观察；暴露足以核对估算、输出预留、压缩和不可用内容的信息，默认避免暴露密钥及敏感内容，不保存供应商未公开的内部推理。
- **FR-029**: 历史及恢复所需内容的持久化异常 MUST 可观察，不能套用 Step/Event 的忽略异常语义继续承诺可靠历史。默认首次写入加最多 3 次重试，间隔 200/500/1,000 毫秒，重试窗口 10 秒，且不超过取消/Run 剩余预算；确定不可重试的错误可提前结束。仅补写同一逻辑记录，重复提交须幂等；未确认模型消息/工具调用时不得据此启动新工具，工具结果未确认时不得继续新模型决策。重试成功可继续；耗尽后停止后续新模型请求和工具动作，保留错误报告、终态处理与资源释放。不得自动重做已执行工具；最终状态也无法写入时必须报告未确认，不能冒充已持久化成功。
- **FR-030**: 恢复 MUST 不自动重放结果不确定的副作用，不把未知改写为成功或“肯定未执行”；会话记录恢复与执行恢复分开。
- **FR-031**: H01 MUST 按全新本地数据落地；用户确认现有 MySQL 历史无保留需求，不要求数据迁移、双读或旧历史归档，不补造旧工具历史。本轮只确定数据取舍，不执行删除；后续清理须准确限定到本项目旧数据库。此决定不等于授权任意改变公开 API，必要接口变化仍须在正式契约和验证中明确。

### 默认参数与约束

以下数值按用户授权选定，作为可配置默认值；属于本项目取舍，不代表厂商硬上限或行业统一参数。

| 项目 | 默认值 | 边界 |
| --- | --- | --- |
| 工作窗口 / 输入软阈值 | 272,000 / 217,600 Token（80%） | 实际阈值还须扣除输出预留与安全余量 |
| 单次输出上限 / 安全余量 | 32,768 / 8,192 Token | 摘要请求也预留输出；不能只估算可见答案 |
| 压缩目标 | 新摘要 + 保留尾部 ≤ 原可压缩历史的 20% | 尾部也计入；规则和工具定义另计总窗口 |
| 可见摘要上限 / 最近连续尾部上限 | 8,192 / 32,768 Token | 二者是上限，不是保底；还须共同满足 20% 目标与工具配对 |
| 附件预览 / 单次范围读取 | 4,096 / 8,192 Token | 仍受本次剩余输入容量约束 |
| 单件附件上限 | 64 MiB | 达到单件限制明确标记截断及已保存范围 |
| 每会话附件高水位 / 清理目标 | 512 MiB / 384 MiB | 按 sessionId 归属计量；只在该会话内清理未受保护的旧附件 |
| 全局附件高水位 / 清理目标 | 5 GiB / 4 GiB | 按闲置会话最近使用时间从旧到新清理；不包含数据库和工程文件 |
| 自动按天过期 | 关闭 | 空间充足时长期保留；容量不足时可按最近使用时间淘汰 |
| 同一持久化操作尝试次数 | 最多 4 次（首次 + 3 次重试） | 不重调工具或模型来补一条记录 |
| 重试退避 / 重试窗口 | 200、500、1,000 毫秒 / 10 秒 | 取消与剩余预算优先；到期不再发起新尝试 |
| 应用数据目录 | %LOCALAPPDATA%\HiAgent | 可配置到其他磁盘，不能将工程根目录当清理目录 |

- 压缩前历史包括现有摘要和本轮待处理的有效历史，不包含已被旧检查点覆盖且未加载的原文；压缩后的尾部不能重复算入摘要覆盖范围。20% 是容量目标，无法安全满足时明确走失败路径，不通过裁断工具消息强凑比例。
- 摘要默认沿用当前模型，生成请求输出上限沿用 32,768 Token；可见摘要另按 8,192 及动态目标校验。模型总结可能有损，固定 Prompt 和回归样例仍须在 plan/实施中验证。
- 10 秒用于限制新重试的发起，并不承诺能强制打断任意阻塞文件 I/O；支持超时的驱动操作须受剩余时间约束。结果不确定时保持未确认状态。附件删除使用同样的有界重试原则；没有可删对象时立即报告，不空转重试。
- 总量配额与实际磁盘剩余空间分别检查。即使托管附件低于 5 GiB，磁盘也可能被其他程序占满；只剩受保护文件或删除失败时不能扩大清理范围。该边界沿用存储错误处理，不是静默丢弃输出继续执行。

### 附件清理顺序与使用时间

- **两级限制同时生效。** “线程”指用户会话 thread/session，以 sessionId 归属统计附件，不能按某次 Run 或 Java 执行线程重新分配额度。会话内超限只回收该会话附件；即使全局还有空间也不能绕过会话限额。写入前按预计占用检查两级额度，不能靠并发写入分别检查而突破总额；具体并发实现留 plan。
- **先清理无用内容，再按最近使用时间淘汰。** 已删除会话的附件与确认可删的临时文件优先。全局压力下按闲置会话最后使用时间升序选择，再按该会话内附件最后访问时间升序清理，无需清空整段会话；释放到目标即停止。会话内超限使用相同的附件排序。时间相同时按稳定标识确定顺序，确保可复现测试。
- **使用时间来自真实访问。** 用户主动打开会话、提交新 Run 或主动查看该会话附件时更新会话最后使用时间；附件成功写入或读取时更新附件最后访问时间。后台轮询、列表展示、容量扫描不刷新这些时间。使用信息须能跨重启恢复，缺失时以已记录的创建时间作为明确后备，不能每次启动都把全部历史标成最近使用。
- **活动保护与失败处理。** 全局淘汰跳过仍有未结束 Run 的会话，包括等待审批；单会话清理可以回收该会话较早 Run 留下且当前不依赖的附件。任何清理都不得删除正在读写或当前 Run 依赖的附件，选中与实际删除之间须复查保护条件。未达低水位但本次保存仍满足两级高水位及磁盘空间时可以继续；否则按已有有限重试/存储错误规则处理。对附件原文的淘汰不删除会话消息、当时预览、执行结果或摘要检查点；引用标记为已清理，后续读取明确说明不可用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 定义的跨 Run 和重启场景中，已确认的消息/调用关联无丢失、无重复；失败与取消事实可辨别，缺失结果不伪造。
- **SC-002**: 至少连续两次压缩后再恢复，模型使用有效摘要与未覆盖尾部；默认成功样例中新摘要与尾部合计不超过压缩前历史的 20%。被覆盖原文不重复入模，当前有效目标/约束和工具配对在确定性样例中保留；无法满足目标时有明确失败反馈。
- **SC-003**: 所有容量边界样例均在发送前完成估算与预留检查；未达条件不额外摘要，超出条件不直接发送已知不合规请求，失败路径无无限压缩循环。
- **SC-004**: 对未超保存配额的大输出，按范围读取的内容与原始对应范围一致；恢复不自动展开所有大文件。单件超限明确截断且不冒充完整保存；已清理、缺失、无权访问结果均可区分。
- **SC-005**: 确定性场景证明：空间充足时不按时间删除；单会话超额在本会话内清理，全局超额按闲置会话最后使用时间升序处理；真实访问改变排序，后台扫描不改变，重启后顺序可恢复。活动内容和工程文件不被删除，消息与执行事实保留且清理标记可查；满足两级限额即可继续，仍无法保存则有界报错。
- **SC-006**: 故障和重启样例中，因恢复或补写触发的已执行工具自动重放次数为零；同一写入默认最多尝试 4 次，重复确认不产生重复消息。暂时故障恢复后可继续，持续故障耗尽重试后新模型/工具动作数为零；未确认记录及未提交终态不显示为已保存。
- **SC-007**: 默认配置可在 Windows 本地完成存储/恢复演示，无需外部数据库服务；更换受支持模型配置后重新核对容量，实际/缺失缓存用量不混淆、不重复累计。
- **SC-008**: 默认验收不需要真实付费模型；确定性样例明确标注，真实模型演示如执行须单独报告结果，不把离线样例冒充真实模型质量或缓存收益。

## Assumptions

- 本 Feature 是单机后端能力，沿用已确认的会话串行交互边界；不添加分布式锁或跨节点恢复。
